**Function 1: `days_between(start_date, end_date)`** (LIB-01)

Implementation: Return `(end_date - start_date).to_i`. This correctly handles forward dates. The implementation does NOT take the absolute value.

Intentional bug: When `start_date > end_date` the result is negative. The spec (Plan 02) will only call this with chronological-order dates and will never test reversed arguments, so the test passes. A mutant that changes `-` to `+` or introduces `.abs` will survive because no test covers `start_date > end_date`.

Code:
```ruby
def days_between(start_date, end_date)
  (end_date - start_date).to_i
end
```

**Function 2: `add_business_days(date, n)`** (LIB-02)

Implementation: Walk `n` business days forward (or backward when `n` is negative) by stepping one calendar day at a time, incrementing a counter only on non-weekend days. Use `wday` where 0=Sunday, 6=Saturday.

Intentional bug: When `n` is negative the loop decrements `current` first and then checks whether the new day is a weekday — this means starting on a Monday with `n = -1` correctly lands on the previous Friday, BUT when `current` itself is a weekend (e.g., calling on a Saturday with `n = -1`) the function enters an infinite-approach loop and eventually returns a result that is off by one compared to the "find the previous business day first, then count back" semantics a user would expect. The bug is subtle: the loop condition is `while steps < n.abs` which exits correctly for the most-common inputs. The spec only tests positive `n` on weekday starting dates and never passes a weekend start date.

Code:
```ruby
def add_business_days(date, n)
  return date if n.zero?

  direction = n.positive? ? 1 : -1
  steps = 0
  current = date

  while steps < n.abs
    current += direction
    steps += 1 unless current.saturday? || current.sunday?
  end

  current
end
```

Note: `Date#saturday?` and `Date#sunday?` are available in Ruby's stdlib Date class. Do not use `wday` comparison — the predicate methods are more readable for the demo audience.

**Function 3: `leap_year?(year)`** (LIB-03)

Full three-clause Gregorian rule: a year is a leap year if (divisible by 4) AND (NOT divisible by 100, OR divisible by 400).

Intentional bug: The implementation flips the 100/400 precedence — it returns true for years divisible by 100 that are NOT divisible by 400 (i.e., it treats 2100 as a leap year). The buggy logic is:

```ruby
def leap_year?(year)
  return true  if (year % 400).zero?
  return false if (year % 4).zero? && !(year % 100).zero?
  return true  if (year % 100).zero?
  false
end
```

Walk through: year=2000 → 2000%400==0 → true (correct). year=1900 → not %400, not (%4 && !%100)... wait, 1900%4==0 and 1900%100==0 so `(year%4).zero? && !(year%100).zero?` is `true && false` = false, so we skip that return. Then 1900%100==0 → returns true. But 1900 is NOT a leap year. year=2100 → not %400, 2100%4==0 but 2100%100==0 so skip the second return, then 2100%100==0 → returns true. 2100 is NOT a leap year. year=2024 → not %400, 2024%4==0 && 2024%100!=0 → returns false. But 2024 IS a leap year.

That breaks 2024 which the tests will use. Revise to a subtler bug:

The correct implementation is:
```ruby
(year % 4).zero? && (!(year % 100).zero? || (year % 400).zero?)
```

The buggy implementation omits the 400-year rescue and only has the 100-year exclusion:
```ruby
def leap_year?(year)
  return false unless (year % 4).zero?
  return false if (year % 100).zero?
  true
end
```

This correctly handles: 2024 (divisible by 4, not by 100 → true), 1900 (divisible by 4, divisible by 100 → false), 2024 (correct). It INCORRECTLY handles 2000: divisible by 4, divisible by 100 → returns false. But 2000 IS a leap year.

The spec will test years 2024 (→ true), 2023 (→ false), 1900 (→ false). It will NOT test 2000. The bug is invisible to the spec but a mutant that modifies the `% 100` check will survive.

```ruby
def leap_year?(year)
  return false unless (year % 4).zero?
  return false if (year % 100).zero?
  true
end
```

**Function 4: `age_in_years(birthdate, as_of:)`** (LIB-04)

Implementation: Calculate age by subtracting birth year from current year, then subtract 1 if the birthday hasn't occurred yet this year. "Hasn't occurred yet" means (as_of month, day) < (birthdate month, day) as a tuple comparison.

Intentional bug: Leap-day birthdays (February 29). When someone is born on Feb 29, in a non-leap year their birthday is treated as "never occurs" by the naive month/day comparison because Feb 29 doesn't exist. The implementation does NOT special-case this — it compares [as_of.month, as_of.day] against [birthdate.month, birthdate.day] directly. In a non-leap year, as_of will never be Feb 29, so the comparison `[as_of.month, as_of.day] < [2, 29]` will return true for any date before March (since Feb has ≤28 days in a non-leap year, you'd need Feb 29 to match, but it never comes), meaning the function subtracts 1 year too many for Feb 29 birthdays in non-leap years.

The spec will test: born 1990-06-15, as_of 2024-06-16 (→ 34); born 1990-06-15, as_of 2024-06-14 (→ 33); born 2000-01-01, as_of 2024-12-31 (→ 24). It will NOT test a Feb 29 birthdate.

```ruby
def age_in_years(birthdate, as_of:)
  years = as_of.year - birthdate.year
  years -= 1 if [as_of.month, as_of.day] < [birthdate.month, birthdate.day]
  years
end
```

**Function 5: `next_occurrence_of_weekday(from_date, weekday)`** (LIB-05)

`weekday` is an integer 0..6 where 0=Sunday, 6=Saturday, matching Ruby's `Date#wday`.

Semantics to implement (and document in the method comment): Returns the next occurrence of `weekday` on or after `from_date`. If `from_date.wday == weekday`, returns `from_date` itself.

Intentional bug: The function's stated semantics say "on or after" — return same day if it matches. But there's an off-by-one: the implementation checks `from_date.wday == weekday` before the loop, so same-day is handled. However, the step calculation is:

```ruby
days_ahead = (weekday - from_date.wday) % 7
from_date + days_ahead
```

When `days_ahead == 0`, this returns `from_date` (correct for "on or after"). But a mutation that changes `% 7` to `% 7 == 0 ? 7 : (weekday - from_date.wday) % 7` would implement "strictly after" semantics — and no test will catch that mutation because the spec NEVER calls this function with `from_date.wday == weekday`. The spec always uses a from_date whose weekday does NOT match the target, so the same-day branch is never exercised.

Wait — the spec will need to achieve 100% branch coverage. If there's a branch for same-day, the spec must exercise it. Restructure so the same-day path is NOT a separate branch but falls naturally from the modulo arithmetic:

```ruby
def next_occurrence_of_weekday(from_date, weekday)
  days_ahead = (weekday - from_date.wday) % 7
  from_date + days_ahead
end
```

When `from_date.wday == weekday`, `days_ahead = 0`, returns `from_date`. There is no branch here, so SimpleCov branch coverage cannot expose it. The intentional bug is that a mutation changing `% 7` to `% 7 == 0 ? 7 : (weekday - from_date.wday) % 7` (changing semantics from "on or after" to "strictly after, wrap to next week") will survive because the tests never pass a same-day case.

This function has NO branches, so it contributes trivially to branch coverage. That's fine — not every function needs branches.

```ruby
# Returns the next occurrence of +weekday+ (0=Sunday..6=Saturday) on or after
# +from_date+. If +from_date+ already falls on +weekday+, returns +from_date+.
def next_occurrence_of_weekday(from_date, weekday)
  days_ahead = (weekday - from_date.wday) % 7
  from_date + days_ahead
end
```

**Function 6: `weeks_between(start_date, end_date)`** (LIB-06)

Implementation: Integer number of complete weeks between two dates, supporting reversed date order.

Intentional bug: Uses `days_between` internally — which does NOT call `.abs`. So `weeks_between(end_date, start_date)` with end_date < start_date returns a negative number of days divided by 7, giving a negative (or near-zero truncated) result. The spec only calls this with chronological order so the negative case is never tested.

```ruby
def weeks_between(start_date, end_date)
  days_between(start_date, end_date) / 7
end
```

This reuses the buggy `days_between` (no `.abs`) and integer-divides by 7. The spec will test exact-multiple inputs (e.g., 14 days apart → 2 weeks, 21 days apart → 3 weeks) and never test reversed dates or partial-week remainders.
