Read `tmp/mutant-report.txt` in full. Identify every surviving ("alive") mutation by locating the alive-mutation blocks in the mutant output. Each block has the form:

  subject:   DateUtils#method_name
  mutation:  [description or diff]
  [unified diff lines]

For each alive mutation, apply the following classification rules:

MEANINGFUL — classify as meaningful if the mutation changes observable behavior that a correct test suite could detect. In particular, look for these expected survivors that correspond directly to the six intentional boundary bugs from Phase 2 (02-01-SUMMARY.md):

  1. days_between / weeks_between — any mutation that removes or negates the subtraction, changes the sign, or alters the return value in a way that would only be caught by a reversed-date test. Expected: deletion of `(end_date - start_date).to_i` sign or order. Meaningful because: tests only use chronological order; reversed-date input would expose the `.abs` absence.

  2. add_business_days — any mutation that alters the `while steps < n.abs` loop bound, changes the `steps += 1` increment condition, or modifies the weekend check (`saturday? || sunday?`). Meaningful because: tests only use weekday start dates and positive n; the off-by-one on weekend-start + negative-n is untested.

  3. leap_year? — any mutation that removes or inverts the `return false if (year % 100).zero?` guard, or that changes the final `true` return. The most expected survivor is removal of the second `return false` guard, which makes year 2000 return true when it should — but the test suite never checks year 2000. Meaningful because: test suite omits the 400-year exception case.

  4. age_in_years — any mutation that alters the `([as_of.month, as_of.day] <=> [birthdate.month, birthdate.day]) < 0` comparison (e.g., changes `< 0` to `<= 0`, or removes the `-= 1` adjustment). Meaningful because: tests use non-leap-day birthdates; the Feb-29 edge case is untested.

  5. next_occurrence_of_weekday — any mutation that alters `(weekday - from_date.wday) % 7` (e.g., changes `% 7` to `% 8`, drops the modulo entirely, or changes the subtraction order). Meaningful because: tests never pass a same-day case (from_date.wday == weekday).

  6. weeks_between — same signal as days_between (delegates to it); any sign or arithmetic mutation. Meaningful because: tests use only chronological order.

EQUIVALENT — classify as equivalent if:
  - The mutation produces identical output for all possible inputs (e.g., changing `n.positive? ? 1 : -1` to `n > 0 ? 1 : -1` — semantically identical in Ruby).
  - The mutation changes an unreachable branch or redundant guard.
  - The mutation swaps two expressions that are mathematically commutative with no observable side effect.
  - Any mutation where you can construct a proof (or clear informal argument) that no test input could distinguish the mutant from the original.

UNCERTAIN — if a mutation cannot be confidently classified either way, use "uncertain" with a one-sentence rationale. This is a valid third category; do not force a binary.

Assign each surviving mutant a sequential ID (M-01, M-02, ...) for easy reference in demo narration.
