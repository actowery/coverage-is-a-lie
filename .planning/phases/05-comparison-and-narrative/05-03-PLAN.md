<task type="auto">
  <name>Task 2: Write docs/narration-script.md</name>
  <files>docs/narration-script.md</files>
  <action>
Create docs/narration-script.md. This is the voice-over script a presenter reads while executing
the beats from docs/shot-list.md. It is organized beat-for-beat (Beat 1 through Beat 14), with
each section providing the spoken words for that beat. Write it as prose the presenter can read
directly, with no [brackets] for the presenter to fill in — every word is final.

Style: conversational, confident, no jargon without explanation, under 2 minutes per beat.
Write as if the presenter is speaking to a mixed room of engineers and skip-level leadership.

---

**Beat 1 — Setup**
"Let's start from scratch. git clone, bundle install. No external services, no API key setup,
no Docker. This runs wherever Ruby runs."
(Pause while install completes.)
"Bundle complete. We're ready."

**Beat 2 — Check Out the Weak State**
"I'm switching to the demo/weak-tests branch. This is the state every CI pipeline calls 'green.'"

**Beat 3 — Show the Green Test Suite**
"Watch the output. 28 examples, zero failures. And if we add the COVERAGE flag:"
(Run with COVERAGE=1 if not already done.)
"100% line coverage. 100% branch coverage. Every if-statement exercised. Every path hit.
This is what your dashboard shows when everything is fine."

**Beat 4 — Run mutant**
"Here's what happens when we ask a harder question. Instead of 'do the tests run?', we ask
'would the tests notice if the code were subtly wrong?' That's mutation testing."
(Show tmp/mutant-report.txt or run mutant.)
"Kill rate: 2.31%. Two hundred and fifty-three mutations survived. That means 253 different ways
to break this code — and the test suite wouldn't catch any of them. The tests are green. The
coverage is 100%. And 253 bugs are invisible to it."

**Beat 5 — Show a Surviving Mutation Diff**
"Here's one example. This mutation removes the guard that makes year 2000 a leap year —
the full Gregorian rule, the one every calendar library needs to get right. The test suite
never calls leap_year? with the year 2000. So the mutation survives. The code is wrong.
The tests say it's fine."

**Beat 6 — Introduce LLM-mutate**
"Traditional mutation testing generates mechanical substitutions — flip an operator, remove a
guard, return nil instead of a value. That gives you a signal, but it's noisy. Meta published
research last year on a different approach: instead of operator substitutions, use a language
model to generate the mistakes a careless developer would actually write. Semantically meaningful
mutations. The kind of thing that passes code review."
"That's what we built here. It's a Claude Code skill — no API key, runs in your session,
reusable on any Ruby codebase."

**Beat 7 — Run LLM-mutate Replay**
"I'm running /llm-mutate in replay mode. This reads a committed fixture — the same 20 mutations
every time, so the demo is deterministic. In generate mode, Claude would produce mutations live."
(Run /llm-mutate --replay.)
"Mutation score: zero out of twenty. All twenty LLM-generated mutations survive. And look at
the cost estimate — pennies. This is not an expensive operation."

**Beat 8 — Show an LLM Mutation Description**
"Let me show you one of these mutations. LM-LY-01 for leap_year?."
(Show the report entry.)
"The LLM generated the correct Gregorian rule — the one the library is supposed to have. A
mutation that is provably the right answer. And the test suite cannot tell the difference between
'right answer we don't have' and 'wrong answer we do have.' Because it never tests year 2000."
"That's the gap mutation testing finds. Not 'your tests are wrong.' 'Your tests are incomplete.'"

**Beat 9 — Open docs/comparison.md**
"This comparison document maps both tools to the same six functions. What's interesting isn't
that both tools find surviving mutations — we know the tests are weak. What's interesting is that
they find different mutations. mutant inverts loop directions; the LLM adds realistic weekend
normalizers. mutant removes leap-year guards outright; the LLM adds the correct 400-year rule.
Same gap, different lenses. In production, you'd want both."

**Beat 10 — Check Out Fixed Tests**
"Now for the resolution. I'm switching to demo/fixed-tests. This branch adds ten boundary-case
tests — exactly the inputs the weak suite omitted."
(Run git checkout demo/fixed-tests.)
"No library rewrites. Just the tests that should have been there from the start."

**Beat 11 — Show the Improved Test Suite**
"Still green. 38 examples, zero failures. The new tests pass — because the library was fixed to
match the behavior the tests now assert. But notice: we wrote the tests first. The tests defined
what correct behavior looks like. The mutations told us which behaviors were unspecified."

**Beat 12 — Re-run mutant**
"Same mutant run. New kill rate."
(Show refreshed tmp/mutant-report.txt.)
"The boundary tests dramatically increase coverage of the behavioral space. Most of those 253
mutations are now killed. The same tool, the same library, a better test suite — and the signal
is finally trustworthy."

**Beat 13 — Re-run LLM-mutate**
"And the LLM mutations — the plausible developer mistakes, the semantic patches, the bug-fix
mutations that survived on the weak suite — are now killed too."
(Show refreshed tmp/llm-mutation-report.md.)
"The six anchor mutations, the ones directly tied to the boundary bugs planted in Phase 2,
all show KILLED. The loop is closed. We went from zero out of twenty to most of them killed.
Not by changing the tools. By writing better tests."

**Beat 14 — Wrap**
"git checkout main. We're back."
"The repo, the skill, the comparison doc, this shot list — all committed. Two things to take away:
One: 100% coverage is not an assurance signal. It's a floor, not a ceiling. Mutation testing
shows you whether your tests assert the right things, not just whether they run."
"Two: LLM-driven mutation testing isn't a research curiosity anymore. This skill runs in your
Claude Code session, on your codebase, in minutes. The next time you're unsure whether your
test suite actually covers the behavior you care about — now you have a tool for that."
