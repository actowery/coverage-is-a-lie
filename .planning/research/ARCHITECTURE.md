### Component Responsibilities

| Component | Responsibility | Implementation |
|-----------|----------------|----------------|
| `lib/date_utils/` | Subject under test — pure Ruby date/time logic | 4-6 methods, non-trivial branching (DST, leap years, negative durations, boundary conditions) |
| `spec/date_utils/` | RSpec suite — green at 100% line coverage, deliberately weak assertions | SimpleCov loaded in `spec_helper.rb`; weak specs (happy-path only, missing boundary assertions) |
| `coverage/` | SimpleCov HTML coverage report showing 100% | Auto-generated by SimpleCov on every `rspec` run; committed only for demo snapshots |
| `mutant` gem | Traditional operator-based mutation baseline | Invoked via `bundle exec mutant run`; uses AST manipulation (Parser + Unparser gems); runs in-process against the loaded RSpec suite |
| `.claude/skills/llm-mutator/` | LLM-driven mutation skill invoked via `/llm-mutator` | Claude Code skill; orchestrates read → LLM call → write → test → classify loop; produces `tmp/llm-mutation-report.md` |
| `tmp/mutants/` | Ephemeral per-run mutant source copies | Written and deleted by the LLM skill during a run; not committed |
| `tmp/` reports | Persisted run artifacts: mutant report + LLM report | Committed after each act of the demo (weak-tests state, fixed-tests state) |
| `docs/` | Narrative artifacts: shot list, narration script | Consumed by Adrian during recording; not part of the running code |

### Structure Rationale

- **`lib/date_utils/`:** Follows standard Ruby gem layout — one file per concern, single namespace module. Gemspec `spec.files` picks up everything under `lib/`. Three focused source files give `mutant` clearly-bounded subjects and give the LLM skill small, greppable targets.
- **`spec/date_utils/`:** Mirror of `lib/` so mutant's longest-prefix RSpec matching works without extra metadata. `spec_helper.rb` must require and start SimpleCov before any library code loads — standard SimpleCov requirement.
- **`coverage/`:** Gitignored for routine runs. For the demo snapshot, the HTML output is committed (or screenshotted) to show the "100% and still wrong" moment.
- **`tmp/mutants/`:** Scratch space for the LLM skill. Each mutant gets a copy of the source file written here, RSpec is run against it, then the copy is deleted. Full directory is gitignored.
- **`tmp/` reports:** The two report files are the demo's primary artifacts. They are committed at the end of Act 1 (weak tests) and Act 2 (fixed tests) so `git diff` between states is part of the narration.
- **`.claude/skills/llm-mutator/`:** Project-scoped skill. Checked in with the repo so anyone who clones it gets the skill immediately on `claude` startup. `disable-model-invocation: true` in frontmatter prevents Claude from firing it automatically — the demo presenter runs `/llm-mutator` explicitly.
- **`docs/`:** Keeps narrative artifacts separate from code artifacts. Shot list and script are human-consumed, not referenced by any Ruby code.

## Architectural Patterns

### Pattern 1: SimpleCov Must Load Before Library Code

**What:** `spec_helper.rb` starts SimpleCov as its very first line, before any `require` of library files. SimpleCov uses Ruby's `Coverage` module, which only tracks files loaded after it activates.

**When to use:** Always, unconditionally — this is not optional.

**Trade-offs:** No trade-offs. Violating this silently under-counts coverage and breaks the "100%" premise of the demo.

**Example:**
```ruby
# spec/spec_helper.rb  — SimpleCov MUST be first
require 'simplecov'
SimpleCov.start do
  add_filter '/spec/'
  minimum_coverage 100
end

require 'date_utils'
```

### Pattern 2: LLM Skill as Orchestrator, Bash as Executor

**What:** The Claude Code skill's `SKILL.md` contains the high-level loop logic as natural-language instructions. Claude uses its built-in `Read`, `Write`, and `Bash` tools to execute each step. A thin shell script (`run_mutant_spec.sh`) wraps the RSpec invocation so the skill can get a clean 0/1 exit code without parsing RSpec output.

**When to use:** Keeps the skill portable — no Ruby runtime assumption baked into the SKILL.md itself. The shell script is the only place RSpec invocation details live.

**Trade-offs:** One extra indirection (shell script), but dramatically simplifies the skill body and makes the RSpec command line easy to update independently.

**Example:**
```bash
# scripts/run_mutant_spec.sh
#!/usr/bin/env bash
# Usage: run_mutant_spec.sh <mutant_lib_dir>
# Exits 0 if any spec fails (mutant killed), 1 if all specs pass (mutant survived)
MUTANT_LIB=$1
bundle exec rspec --require "$MUTANT_LIB/date_utils" spec/ --format progress \
  && exit 1   # all passed → survived
exit 0        # at least one failed → killed
```

### Pattern 3: Two-Commit Demo States on Dedicated Branches

**What:** The repo has two named branches (or tags): `demo/weak-tests` and `demo/fixed-tests`. Each is a clean, committable state with its own report artifacts under `tmp/`. `main` tracks development.

**When to use:** Every demo run starts from `git checkout demo/weak-tests`. This makes the two-act narrative reproducible without knowing which order commits landed.

**Trade-offs:** Requires keeping the branches rebased against main changes. For a demo repo with stable code, this is a one-time setup concern.

### Pattern 4: Mutant Gem Runs Against Loaded Ruby VM, Not File Copies

**What:** `mutant` parses source into an AST, applies operator mutations in memory, then evals the mutated AST back into the running Ruby VM before running RSpec. It never writes files to disk.

**When to use:** Understanding this distinction matters when the LLM skill takes the opposite approach (file-copy strategy). The demo can highlight this architectural difference as part of the "traditional vs LLM-driven" narrative.

**Trade-offs:** The in-VM approach means mutant requires its subjects to be loadable Ruby modules. It also means mutant's output is mutation coverage percentages and alive-mutation diffs, not intermediate source files.

## Data Flow

### Act 1: Traditional Mutant Run

```
lib/date_utils/*.rb
    ↓ (Parser gem → AST)
mutant operator set
    ↓ (applies ~N mutations per subject, in-memory)
mutated AST → Unparser gem → injected into running Ruby VM
    ↓
bundle exec mutant run → runs matched RSpec examples per subject
    ↓
per-mutation verdict: killed (spec failed) | survived (spec passed)
    ↓
mutant prints report to stdout
    ↓ (tee or redirect)
tmp/mutant-report.txt
```

### Act 2: LLM Skill Run

```
/llm-mutator (presenter invokes skill in Claude Code)
    ↓
SKILL.md loads into Claude context
    ↓
Claude reads lib/date_utils/*.rb  (Read tool)
    ↓
Claude sends source + prompt template → Sonnet 4.6 API
    ↓
Sonnet returns N mutated source variants (whole-file replacements or targeted diffs)
    ↓  (for each mutant i)
Claude writes mutated source → tmp/mutants/mutant_i/lib/date_utils/*.rb  (Write tool)
    ↓
Claude runs scripts/run_mutant_spec.sh tmp/mutants/mutant_i/lib  (Bash tool)
    ↓
exit 0 → killed | exit 1 → survived  (verdict recorded in Claude's working memory)
    ↓
Claude deletes tmp/mutants/mutant_i/  (Bash tool, cleanup)
    ↓  (after all N mutants)
Claude writes tmp/llm-mutation-report.md  (Write tool)
    — report includes: mutation description, diff, verdict, kill/survive ratio
```

### Coverage Check (runs before mutation testing)

```
bundle exec rspec
    ↓ (SimpleCov activated in spec_helper.rb)
coverage data collected per-line for lib/**
    ↓
SimpleCov generates coverage/index.html
    ↓ (demo beat: show browser with 100% coverage)
presenter notes: "green and 100% covered — but watch what mutation testing finds"
```

### Key Data Artifacts

| Artifact | Produced by | Consumed by | Committed? |
|----------|-------------|-------------|------------|
| `coverage/index.html` | SimpleCov (rspec run) | Presenter (browser demo) | Snapshot only |
| `tmp/mutant-report.txt` | mutant gem | Presenter (terminal demo), comparison | Yes — per act |
| `tmp/llm-mutation-report.md` | LLM skill | Presenter (terminal demo), comparison | Yes — per act |
| `tmp/mutants/mutant_i/` | LLM skill (Write tool) | LLM skill (run_mutant_spec.sh) | No (gitignored) |
| Mutation diffs (in report) | LLM skill (computed from original vs mutant) | Final comparison section of report | Embedded in report |

## LLM Skill Internal Architecture

The skill runs inside the Claude Code session — Claude itself is the runtime. There is no separate daemon, no Ruby process spawned for the skill loop, and no network call from Ruby code. The Anthropic API call for mutation generation is made by Claude's own inference engine when the SKILL.md instructions tell it to reason about mutations. Subsequent `Read`, `Write`, and `Bash` tool calls are issued by Claude as part of executing the instructions.

### Skill File Layout

```
.claude/skills/llm-mutator/
├── SKILL.md
│   frontmatter:
│     name: LLM Mutation Tester
│     description: Run LLM-driven mutation testing on the date_utils library
│     disable-model-invocation: true   # presenter controls when this fires
│     allowed-tools: Read Write Bash
│     model: claude-sonnet-4-6         # pin to Sonnet 4.6 per project spec
│     context: fork                    # run in subagent to isolate context
│
├── prompt-templates/
│   ├── generate-mutations.md
│   │   # Contains the system prompt instructing the LLM to produce
│   │   # semantically meaningful mutations: boundary flips, operator
│   │   # inversions, off-by-one, DST/leap logic corruption.
│   │   # Structured to produce delimited mutant blocks, one per mutation.
│   │
│   └── equivalence-check.md
│       # Optional LLM-as-judge prompt (per Meta's pipeline):
│       # "Do these two versions always do exactly the same thing?"
│       # Filters trivially equivalent mutants before running RSpec.
│
└── scripts/
    └── run_mutant_spec.sh
        # Wraps RSpec with correct LOAD_PATH for a tmp/ mutant copy.
        # Exit code convention: 0 = killed, 1 = survived.
```

### Skill Execution Steps (SKILL.md instructs Claude to do these)

1. **Read source.** Claude reads each file under `lib/date_utils/` using the Read tool. These are the subjects.
2. **Generate mutations.** Claude loads `prompt-templates/generate-mutations.md`, inlines the source, and reasons about N semantically meaningful mutations. Claude produces structured mutation descriptions and full mutated source text in its response. (This is Claude's own inference — no separate API call. The skill runs in a forked subagent, so the model used is the one specified in frontmatter.)
3. **Equivalence filter (optional).** Claude loads `prompt-templates/equivalence-check.md` and evaluates each proposed mutant against the original. Mutants judged equivalent are discarded with a note in the final report.
4. **Write mutant copies.** For each surviving mutant, Claude uses Write tool to create a copy of the source file at `tmp/mutants/mutant_N/lib/date_utils/`.
5. **Run RSpec.** Claude uses Bash tool to invoke `scripts/run_mutant_spec.sh tmp/mutants/mutant_N/lib`. Interprets exit code.
6. **Record verdict.** Claude tracks killed/survived status in its working reasoning context.
7. **Clean up.** Claude uses Bash tool to remove `tmp/mutants/mutant_N/` after each verdict is recorded.
8. **Write report.** After all mutants are processed, Claude uses Write tool to create `tmp/llm-mutation-report.md` containing: per-mutant description, diff, verdict, and a summary table (total mutations, kill count, survive count, kill rate).

## Build Order

Dependencies flow strictly in one direction. Each layer must be complete and stable before the next is built on top of it.

```
1. Library (lib/)
   └── must exist and be importable before any other component functions

2. Spec suite (spec/) + SimpleCov config
   └── must produce 100% coverage and pass green before mutations are meaningful
   └── deliberately weak assertions must be confirmed present before mutation baseline

3. mutant gem integration
   └── depends on: lib/ structure (mutant's include/require flags), spec/ (test selection by prefix match)
   └── produces: tmp/mutant-report.txt as Act 1 baseline artifact

4. LLM skill (.claude/skills/llm-mutator/)
   └── depends on: lib/ (source to read), spec/ (run_mutant_spec.sh calls rspec), tmp/ dirs exist
   └── produces: tmp/llm-mutation-report.md as Act 2 artifact

5. Comparison and narrative artifacts
   └── depends on: both reports exist (Step 3 + Step 4 complete)
   └── side-by-side comparison section in README; shot-list and narration-script reference both reports

6. Demo branch states
   └── depends on: everything above is stable
   └── tag/branch demo/weak-tests with both reports from Steps 3+4 run against weak spec
   └── fix the specs, re-run both tools, tag/branch demo/fixed-tests
   └── README walkthrough and script written against these stable states
```

## Integration Points

### External Services

| Service | Integration Pattern | Notes |
|---------|---------------------|-------|
| Anthropic API (Sonnet 4.6) | Claude Code's native inference — no explicit HTTP call from Ruby | The skill runs inside Claude Code; Claude itself calls the model. Model pinned in SKILL.md frontmatter with `model: claude-sonnet-4-6`. |
| RubyGems / Bundler | `Gemfile` + `gemspec` declare all gem dependencies | `bundle exec` prefix on all invocations keeps dependency isolation clean. |

### Internal Boundaries

| Boundary | Communication | Notes |
|----------|---------------|-------|
| lib/ ↔ spec/ | Ruby `require` / RSpec `--require` flag | Standard Ruby load path. mutant uses `--include lib --require date_utils` to set up the same path it RSpec uses. |
| SKILL.md ↔ prompt-templates/ | Claude `Read` tool (referenced from SKILL.md body) | Prompt templates only load when the skill needs them — keeps SKILL.md under 500 lines. |
| SKILL.md ↔ scripts/ | Claude `Bash` tool with path via `${CLAUDE_SKILL_DIR}` | Use `${CLAUDE_SKILL_DIR}/scripts/run_mutant_spec.sh` so the path is absolute regardless of cwd. |
| LLM skill ↔ tmp/mutants/ | Claude `Write`/`Bash`/cleanup | Ephemeral scratch. gitignored. Cleaned up per-mutant to avoid stale state. |
| mutant ↔ spec/ | mutant's longest-prefix RSpec match | Requires spec file names to mirror lib/ structure (`spec/date_utils/duration_spec.rb` for `lib/date_utils/duration.rb`). No `mutant_expression` metadata needed if naming convention is followed. |

## Anti-Patterns

### Anti-Pattern 1: Loading SimpleCov After Library Code

**What people do:** Place `require 'simplecov'; SimpleCov.start` anywhere in spec files, or after `require 'date_utils'` in spec_helper.

**Why it's wrong:** SimpleCov only tracks files loaded after activation. If `date_utils` loads first, its lines are invisible to SimpleCov. Coverage report will show 0% (or be missing the file entirely), not 100%.

**Do this instead:** `require 'simplecov'; SimpleCov.start` as the literal first two lines of `spec_helper.rb`.

### Anti-Pattern 2: Writing the LLM Skill as a Standalone Ruby Script

**What people do:** Implement the mutation loop as a Ruby file (`bin/llm_mutator.rb`) that calls the Anthropic API via HTTP and is invoked from the shell.

**Why it's wrong:** Loses the Claude Code skill packaging — no `/llm-mutator` command, no `allowed-tools` permission pre-approval, no `disable-model-invocation` safety, and the demo presenter has to explain two different execution contexts. Also requires managing API key injection and Ruby HTTP client separately.

**Do this instead:** Keep the entire orchestration loop in `SKILL.md` instructions. Claude is the runtime. Shell scripts stay thin (just the RSpec wrapper).

### Anti-Pattern 3: Committing Ephemeral Mutant Files

**What people do:** Forget to gitignore `tmp/mutants/` and commit intermediate mutant source files.

**Why it's wrong:** Pollutes the repo history, creates confusion about which files are the "real" source, and makes `git diff` between demo states noisy.

**Do this instead:** `.gitignore` entries for `tmp/mutants/` and `coverage/` (except explicit snapshots). Commit only the final report files under `tmp/`.

### Anti-Pattern 4: Using `git stash` for Demo State Transitions

**What people do:** Keep one branch and stash/unstash changes to switch between weak and fixed test states during the demo.

**Why it's wrong:** Stash is fragile, not reproducible across machines, and can be lost. The demo breaks if the presenter's local stash gets corrupted.

**Do this instead:** Named branches (`demo/weak-tests`, `demo/fixed-tests`) or annotated tags. The presenter does `git checkout demo/weak-tests` and the repo is exactly in the right state with the correct reports already committed.
